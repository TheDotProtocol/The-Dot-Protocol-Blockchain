2. Critical & High Findings

CRITICAL C-01: Single EOA Admin Controls Entire Token Supply

Contracts: DPC20, Oracle, Stabilization, Governance, Bridge

Description: A single externally-owned account (EOA) holds DEFAULT_ADMIN_ROLE on all deployed contracts. This private key is the single point of failure. If compromised, an attacker can:

  • Mint unlimited tokens (draining the entire 1T supply)
  • Rebase the token, inflating/deflating all balances
  • Pause all token transfers globally
  • Add/remove bridge validators
  • Modify oracle price feeds
  • Execute arbitrary governance proposals

Impact: Total loss of all user funds across the ecosystem.

Remediation: Deploy a Gnosis Safe multisig (3-of-5 minimum) as admin on all contracts. Add a 48-hour timelock to critical operations (rebase, mint, pause). Transfer DEFAULT_ADMIN_ROLE to the multisig immediately.

CRITICAL C-02: Rebase Function Can Drain Token Supply Without Governance

Contract: DPC20.sol, line 67-78

Description: The rebase(int256 delta) function allows REBASE_ROLE to mint or burn tokens with a single transaction and no governance vote, timelock, or multi-step confirmation. A negative delta burns tokens from the contract's own balance (which holds the minted rebase amount), but a positive delta mints new tokens up to MAX_SUPPLY.

Attack vector: Compromised REBASE_ROLE → rebase(+999999999 ether) → instant minting of trillions of tokens to attacker.

Remediation: Add TimelockController (OpenZeppelin) to rebase operations. Require governance proposal → voting period → timelock delay → execution. Cap rebase delta to ±5% of total supply per 30-day period.

CRITICAL C-03: Hardcoded Private Key in Deploy Script

File: packages/contracts/scripts/deploy-mock-tokens-ethers.js, line 6

Description: A deployer private key is hardcoded in plaintext: REDACTED_KEY. This key controls 58M TDOT on testnet and is committed to the Git repository.

Impact: Anyone with repo access can drain the deployer's funds. If this key is reused on mainnet, all mainnet funds are at risk.

Remediation: Remove hardcoded key immediately. Use environment variables only. Rotate the key if it has ever been used on mainnet. Add the deploy script to .gitignore patterns.

CRITICAL C-04: JWT Secret with Hardcoded Fallback

File: apps/hexchange-api/src/middleware/auth.js, line 3

Description: const JWT_SECRET = process.env.JWT_SECRET || "hexchange-dev-secret-key-change-in-production"; — The fallback is a well-known string that will be used if the env var is not set (which it currently isn't on any deployment).

Impact: Any attacker can forge valid JWT tokens and impersonate any user, including admins. This allows unauthorized order placement, wallet access, and profile modification.

Remediation: Generate a cryptographically random 64-byte secret. Require it via env var with no fallback — crash on startup if missing. Rotate immediately if any token was issued with the default.

CRITICAL C-05: Besu RPC CORS Wildcard on Mainnet

File: infra/besu/mainnet/docker-compose.yml, all validator configs

Description: --rpc-http-cors-origins=* on all mainnet nodes allows any website to make RPC calls. Combined with the exposed RPC ports, any malicious webpage can read chain state and submit transactions using the node's connection.

Impact: Enables cross-site RPC attacks, chain data exfiltration, and potentially transaction manipulation if combined with wallet injection.

Remediation: Restrict CORS to known domains: --rpc-http-cors-origins=https://hexchange.YOUR_DOMAIN.com,https://YOUR_DOMAIN.com. Restrict RPC access to localhost or VPN.

CRITICAL C-06: Bridge Has No Cross-Chain Validation

Contract: Bridge.sol

Description: The Bridge contract is deployed but has no functioning cross-chain counterpart. It accepts submitAttestation calls from any RELAYER_ROLE holder without validating actual events on a source chain. This means a compromised relayer can mint tokens on the destination chain without any real source-chain deposit.

Impact: Unlimited token minting on any chain via forged attestations.

Remediation: Implement proper SPV proofs or use a trusted oracle network (Chainlink CCIP, LayerZero) for cross-chain message validation. Never ship bridge to production without verifiable cross-chain state.

HIGH H-01: Escrow ETH Trapped in Contract

Contract: HexchangeEscrow.sol, acceptAndPay() and resolveDispute()

Description: ETH sent via acceptAndPay() is received by the contract but never forwarded to the seller. When resolveDispute() releases to seller, only ERC20 tokens are sent — ETH remains trapped. The contract has a receive() function accepting ETH but no withdrawal mechanism.

Remediation: Add an ETH withdrawal function: function withdrawETH(uint256 amount) external onlyAdmin { payable(admin).transfer(amount); }. Fix resolveDispute to also handle ETH.

HIGH H-02: Order Book Auth Not Enforced

File: apps/hexchange-api/src/index.ts, line 66

Description: The order submission endpoint uses optionalAuth and falls back to req.body.user — meaning anyone can submit orders as any wallet address. The cancel endpoint has no auth at all, only checking if the user in the body matches.

Remediation: Make auth required for order submission. Validate that req.user.id matches the order creator. Add auth to cancel endpoint.

HIGH H-03: No SQL Injection Protection

File: apps/hexchange-api/src/routes/auth.js and engine.ts

Description: While parameterized queries are used (good), the pair parameter from URL paths is decoded and passed directly. The parseInt(req.query.limit) has a NaN fallback but could be exploited. More critically, the order book's seedOrderBook() in engine.ts uses string interpolation in some internal methods.

Remediation: Add input validation middleware (e.g., express-validator). Sanitize all URL-decoded parameters. Validate numeric ranges.

HIGH H-04: Custom JWT Implementation (Not Using Library)

File: apps/hexchange-api/src/middleware/auth.js

Description: JWT creation and verification is implemented from scratch using raw HMAC. While functionally correct, custom crypto implementations are prone to subtle bugs (timing attacks, algorithm confusion, missing checks). The verifyToken uses string comparison for signatures, which is not constant-time.

Remediation: Replace with jsonwebtoken library. Use crypto.timingSafeEqual for signature comparison at minimum.

HIGH H-05: All Validator Node Keys on Host Filesystem

File: infra/besu/mainnet/networkFiles/

Description: All 7 validator private keys are stored in plaintext on the host filesystem, accessible to any process or user with disk access. These keys control consensus on mainnet — compromise allows chain reorganization.

Remediation: Use hardware security modules (HSM) or AWS KMS for validator keys. At minimum, use file permissions (chmod 600) and move keys out of the repository.

HIGH H-06: Token Names Mismatch — DPC20 Named "Dot Protocol Coin" (3DOT)

Contract: DPC20.sol, line 24

Description: The DPC20 contract on both testnet and mainnet uses name "Dot Protocol Coin" and symbol "3DOT". On testnet, the token should be "TDOT" (The Dot Protocol). This creates confusion and potential phishing vectors.

Remediation: Deploy a separate TDOT contract for testnet with correct naming, or accept the current naming and document it clearly.

7. Bridge Security

⚠️ Bridge is NOT Production-Ready

The bridge contract has the correct structure for a cross-chain bridge but lacks:

  • Cross-chain state verification: Attestations are accepted from any RELAYER_ROLE holder without validating source-chain events
  • Nonce replay protection: Same attestation can be submitted multiple times
  • Quorum requirement: Single relayer can approve any transfer
  • Rate limiting: No per-address or per-token transfer limits
  • Circuit breaker: No emergency pause if bridge is compromised

Recommendation: Do NOT use the bridge for real funds until it has a validated cross-chain messaging layer (Chainlink CCIP, Axelar, or LayerZero).

8. Wallet Security

Wallet App is Currently a Library, Not a Product

  • No actual wallet functionality: The app shows mock balances and static HTML
  • No key management: No seed phrase generation, no key storage, no signing
  • No transaction signing: Cannot send or receive tokens
  • Security recommendation: Use WalletConnect v2 or Web3Modal for wallet integration rather than building custom key management. Custom wallet implementations have an extremely high vulnerability rate.

10. Remediation Roadmap

🔴 Phase 1: Critical Fixes (Before Any Production Use) — 1-2 Days

  1. Remove hardcoded private key from deploy scripts
  2. Rotate JWT secret — generate 64-byte random, require via env
  3. Restrict CORS on all Besu nodes to known origins
  4. Enforce auth on order submission endpoint
  5. Fix Escrow ETH trap — add withdrawal function

🟠 Phase 2: High-Priority (Before Mainnet Launch) — 1-2 Weeks

  1. Deploy Gnosis Safe multisig as admin on all contracts
  2. Add TimelockController to DPC20 critical functions
  3. Implement proper bridge validation (CCIP/LayerZero/Axelar)
  4. Generate separate validator keys per network
  5. Add TLS to all RPC endpoints
  6. Replace custom JWT with jsonwebtoken library
  7. Add CSP headers to all frontend apps

🟡 Phase 3: Medium-Priority (Before Public Launch) — 2-4 Weeks

  1. Get professional audit — CertiK, Trail of Bits, or OpenZeppelin
  2. Add input validation middleware across all API routes
  3. Move validator keys to HSM or AWS KMS
  4. Add emergency pause to Presale and Governance
  5. Implement oracle decentralization — multi-source price feeds
  6. Add monitoring — alerting on unusual mint/rebase/pause events

🟢 Phase 4: Nice-to-Have (Post-Launch Hardening)

  1. Add formal verification for critical contract functions
  2. Implement bug bounty program
  3. Add on-chain monitoring (Tenderly, Forta)
  4. Implement circuit breakers for unusual activity
  5. Add rate limiting per token pair in Router
